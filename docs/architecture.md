# Why Stellenpilot is built this way

The README says what Stellenpilot does. This page says why some parts look the way they do, so a change does not undo a decision by accident. Each section names the file to read next. Plans for a phone and desktop app are in [multiplatform.md](multiplatform.md).

## A standard library HTTP server, one SQLite connection and a lock

`server.py` runs on `http.server.ThreadingHTTPServer` and uses no web framework. The server has one user on one machine sending a few requests a second, so a framework would add a dependency to keep patched and more code to review while giving nothing back, and leaving it out keeps the Windows and macOS app builds small. The price is plain routing (`if self.path == ...`) and no validation layer, so every handler checks its own input. Because the server is threaded, all dashboard requests share one `DB` object, which is one SQLite connection opened with `check_same_thread=False`, and a `threading.Lock` lets only one request use it at a time; one connection behind a lock is simpler than a pool and is enough for one person. Work that can take minutes with a local model (adding a job by link, Gmail sync, reading a CV, building documents, see `SLOW_POSTS`) and the daily search in `pipeline.py` open their own connection and run outside the lock, so the dashboard keeps answering while the AI writes. `/api/progress` and `/api/check` skip the lock for the same reason. Writes from those separate connections are queued by SQLite's own file lock, and the 30 second `timeout` in `db.py` makes a writer wait instead of failing with "database is locked". The missed run catch up checks and claims `run_state` under the same lock as the Search button, so two searches can never start at once.

## The Host header and `X-Jobhunt`: DNS rebinding and cross site requests

Binding to `127.0.0.1` keeps other computers out, but not other websites, because a page you open runs in your browser on your own machine. Two attacks matter. In DNS rebinding, a site first resolves its name to its own server and then to `127.0.0.1`, so its page counts as same origin with the dashboard and could read your jobs and CV. The browser still sends that site's name in the `Host` header, so `_host_ok` refuses every request, read or write, whose host is not `127.0.0.1`, `localhost` or `[::1]`. The port is ignored on purpose so Docker port mappings keep working, which is also why Docker can listen on all interfaces inside the container and still only accept your browser. In a cross site request, any page can make your browser send a POST to localhost and the server would act on it even though the page never sees the answer. So every POST and PATCH also goes through `_guard`, which demands the header `X-Jobhunt: 1` and, when an `Origin` is sent, a local one. Another site cannot add a custom header without a CORS preflight, this server never answers preflights, and so the real request is never sent. The dashboard's own `fetch` in `web/index.html` adds the header. GET requests only get the Host check: no GET route changes data or opens anything (opening a folder or document is a POST), and the same origin policy stops another site from reading a GET answer. This guard is the reason there is no login today, and it also refuses phones by design; remote access needs device tokens, see [multiplatform.md](multiplatform.md).

## `manual.py`: resolve the host once and pin the connection to that address

Adding a job by link means Stellenpilot fetches a URL someone typed or pasted, which is server side request forgery waiting to happen: a link to your router, to `127.0.0.1:8765` itself or to a cloud metadata address would make the app read something private. `resolve_public` looks the host name up once and refuses the link if any address it returns is not on the public internet, including IPv4 written as IPv6 (`::ffff:127.0.0.1`). The check alone is worthless if the fetch then does a second lookup, because the attacker controls their DNS server and can answer with a public address the first time and `127.0.0.1` the second (rebinding, this time aimed at the server). So `_PinnedHTTP` and `_PinnedHTTPS` connect to exactly the checked address while still sending the real `Host` header, and for HTTPS they verify the certificate against the real name through SNI, so pinning does not weaken TLS. Every redirect is a new hop and goes through the same check and pin, up to five. There is no proxy fallback, because a company proxy can reach internal hosts this code has no way to check. The same check refuses LinkedIn, StepStone, Indeed, XING and Glassdoor on every hop, because their terms forbid automated access; pasting the ad text is the supported way. Tests are in `tests/test_ssrf.py`.

## `tailor.py`: why the truth guard is a vocabulary check and not another model call

The guard exists because a model may invent experience, and asking a model to check a model repeats the same weakness, worst of all with the small 2B and 4B models the built in AI uses. A rule based check gives the same answer for the same text every time, runs in milliseconds, works with the AI switched off and is covered by offline unit tests. It also does not have to check much, because the CV bullets are copied word for word from `profile.toml` and `_valid_plan` clamps the model's choices to indexes that exist; only the summary and the cover letter are generated. `unsupported_claims` rejects any number that is not in your profile (your Learning list excluded) or in the job title and company, any German or English level higher than the one you stated, and any tool from `score.VOCAB` that your experience does not mention. A missing tool is allowed only in an honest sentence: "I have not used X yet" or "I would like to learn X" for a tool the ad names, and "I am learning X" for a tool on your Learning list; a sentence that also says used, built, ran or similar never counts. When the guard fails, the summary falls back to your default summary, and the letter gets one retry that names the problem before a template letter is used. What it misses: tools that are not among the 54 in `VOCAB`, numbers written as words ("twelve"), vague claims ("led the team", "expert in"), and true facts put in a false context, for example a "3" from "3 years" reused as "3 pipelines in production". That is why the README asks you to read every document before you send it.

## `builtin.py`: why downloads are pinned by SHA256 and by commit

The built in AI downloads an executable (llama.cpp's `llama-server`) and a 1.3 to 2.7 GB model, then runs them, which makes it the riskiest thing the app does. The engine is pinned to one release build (`LLAMA_BUILD`), and each model URL contains a fixed Hugging Face commit instead of `main`, which the uploader can change at any time. The pin makes every user get the same files that were tested, so a bug report about scoring or a result in `docs/results.md` refers to one exact model. The hash protects the download itself: `_fetch` streams into a `.part` file, computes its SHA256 on the way and keeps the file only if it matches the value written in the source; otherwise it is deleted and never run, and a file with no known checksum is refused outright. Pinning alone would still trust whatever GitHub or Hugging Face serves under that name, and a hash alone would not say which file to fetch, so both are needed. The cost is that an upgrade means changing the build name, URLs and hashes together and running the tests again. Once running, the engine listens on `127.0.0.1` on a random port, needs a fresh random API key from every start, and stops after ten idle minutes to free memory.

## Why `think` is off for Qwen by default

Qwen3, Qwen3.5 and Gemma 4 reason in a hidden block before they answer unless told not to. Stellenpilot asks for short JSON (a score, a CV plan, a letter body), and on a CPU every extra token costs real time, so hundreds of reasoning tokens per call add up over a daily run of dozens of jobs. Reasoning tokens are also produced inside the same `max_tokens` budget (1200 for a plan, 900 for a letter), so a long think can cut the answer off and leave broken JSON. So `llm.think` defaults to false: Ollama gets `think: false`, and the built in engine gets `enable_thinking: false` through the chat template and is started with `--reasoning-budget 0` as well. If a model or an older Ollama rejects the option, it is dropped and the request is sent again, and `strip_thinking` removes any `<think>` block that leaks through anyway. Set `think = true` under `[llm]` to turn it back on. Whether thinking improves scores on your jobs has not been measured; `stellenpilot eval` is the way to find out on your own labels.
